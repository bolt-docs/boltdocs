Boltdocs 3.4 prepares the migration to 4.0, while the long-lived `4.0` branch develops the new architecture in parallel. The goal is a smaller, clearer core with explicit package boundaries, optional integrations, and faster edited builds.

## What changes in 3.4.0

The 3.4 line remains the compatibility branch. It will focus on compatible improvements, performance work, bug fixes, and documentation. We will not require 4.0-only packages for a normal 3.4 installation.

The 3.4 release will also prepare the migration by introducing shared contracts, documenting deprecations, and measuring builds against Docusaurus Faster with reproducible cold, warm, edited, dev-startup, and output scenarios.

## The 4.0 package boundaries

The target structure is:

```text
@boltdocs/contracts
  ├─ @boltdocs/core-node
  ├─ @boltdocs/runtime
  ├─ @boltdocs/ssg
  ├─ @boltdocs/processor-satteri
  └─ @boltdocs/plugin-*
```

`@boltdocs/contracts` will contain the shared types and interfaces for routes, manifests, plugins, build contexts, and invalidation. It will not depend on Node.js, Vite, React, or any integration package.

`@boltdocs/core-node` will own configuration, routes, frontmatter, plugin lifecycle, build orchestration, and dev-server state. `@boltdocs/runtime` will own browser-facing React, routing, hydration, navigation, and client contexts. `@bdocs/ssg` will keep the client/server builds, SSR rendering, critical CSS, workers, output, and page cache.

## Integrations become optional

Search, Mermaid, Math, Ask AI, image optimization, RSS, and LLMS integrations will remain available, but they will be consumed through public plugin contracts instead of being hard-coded into the core. A site should be able to remove an integration without changing the framework engine.

This separation will make integrations easier to update independently and will prevent optional dependencies from entering the browser or Node bundles unnecessarily.

## Incremental builds

The major performance goal is to make an edited build proportional to the change:

1. detect the changed source and frontmatter;
2. recompile only the changed MDX document;
3. resolve the route's client, server, CSS, and plugin dependencies;
4. invalidate only affected modules;
5. reuse safe client and server artifacts;
6. rerender only affected routes;
7. rewrite current asset references for cached HTML.

A text-only edit should not invalidate unrelated pages or force a complete SSG render. Benchmarks will track the number of recompiled, rerendered, and cached routes in addition to elapsed time.

## How the branches work

`develop` is the stable 3.4 line. `4.0` is the long-lived major-version line. Small feature branches are created from `4.0`, reviewed independently, and merged back after their tests and benchmarks pass. Stable fixes from `develop` are merged into `4.0` regularly.

This lets us improve 3.4 for current users while developing the new package graph and migration tooling without forcing an immediate upgrade.

## Migration support

Before 4.0 is published, we will provide:

- a package and import migration guide;
- compatibility adapters where they are safe;
- codemods for the most common breaking changes;
- diagnostics for private imports and unsupported plugin patterns;
- a clear list of removed APIs and replacement packages;
- performance and build-output comparisons for standard and complex documentation sites.

The complete internal checklist is tracked in [`ROADMAP-4.0.md`](https://github.com/bolt-docs/boltdocs/blob/4.0/ROADMAP-4.0.md).

## What 4.0 means for users

Most 3.4 projects should continue to work while the migration is prepared. When 4.0 is released, the upgrade path will depend on whether a project uses public APIs, custom plugins, custom layouts, or private internal imports. The migration guide will call out each path and provide a recommended destination package.

The guiding principle is simple: every boundary must either reduce coupling, improve incremental builds, or make integrations independently maintainable.
