Every primitive in Boltdocs is **style-neutral**. Behavior lives in `@bdocs/primitives` and `@bdocs/runtime`; the default look lives in `@bdocs/theme-neutral`. Your theme owns every visual decision. This is what lets two completely different sites run on the same component code.

```text
primitive  →  <aside data-sidebar-root> + data-active, data-open, data-depth …
               structure + behavior + state (no colors, no sizes)

theme      →  native CSS targeting those data-* attributes
               colors, borders, spacing, transitions — all yours
```

## The Contract

A primitive renders semantic HTML, wires up behavior (open/close, keyboard navigation, active detection, scroll tracking) and exposes its **state through `data-*` attributes that are present only when true**. Your theme never needs to know *how* the state is computed — only *that* it exists.

```tsx
// What the framework renders when a sidebar link is the active page:
<a href="/docs/guides" data-active aria-current="page" …>
  Guides
</a>
```

```css
/* What your theme does with it: */
a[data-active] {
  color: var(--bdocs-primary);
  background: var(--bdocs-primary-soft-10);
}
```

The default theme ships **native CSS** in `src/styles/`. You do not need Tailwind, and none of the core packages assumes a CSS framework.

## Which States Does Each Primitive Expose?

| Primitive | State attributes | Behavior |
| :--- | :--- | :--- |
| **`Disclosure`** (sidebar groups) | `data-open`, `data-collapsible`, `aria-expanded`, `aria-controls` | Expand/collapse, active auto-expand |
| **`Navbar`** | `data-open`, `aria-expanded`, `aria-controls` | Mobile drawer, hover dropdown, outside press, Escape |
| **`Tabs`** | `data-selected`, `aria-selected`, `aria-controls` | Roving tabindex, arrow/Home/End navigation |
| **`Group`** | `data-orientation`, `data-disabled` | Accessible grouping semantics |
| **Scroll spy** (`OnThisPage`) | `data-active`, `data-level`, `data-otp-*` | IntersectionObserver tracking, indicator geometry, auto-scroll |

## Where the Defaults Live

The look you get out of the box is implemented in `@bdocs/ui-base`:

- `src/composition/` — thin styled wrappers over `@bdocs/primitives`.
- `src/ui-base/` — the assembled UI (navbar, sidebar, search dialog, …).
- `src/styles/components/` — one native CSS file per component.

`@bdocs/theme-neutral` assembles those pieces into the default docs layout and owns the MDX components; it re-exports the UI API for backwards compatibility.

Every wrapper accepts `className` slots (and `itemClassName`, `linkClassName`, `indicatorClassName`, `fadeClassName` where the slot repeats per item). Those class names are merged with the defaults and can be replaced entirely.

```tsx
// docs/src/theme/on-this-page.tsx
import { OnThisPage as Primitive } from '@bdocs/ui-base/composition'

export function OnThisPage() {
  return (
    <Primitive.Root className="my-toc">
      <Primitive.Header className="my-toc__header">On this page</Primitive.Header>
      <Primitive.Tree
        headings={currentRoute.headings}
        className="my-toc__list"
        itemClassName="my-toc__item"
        linkClassName="my-toc__link"
        indicatorClassName="my-toc__indicator"
      />
    </Primitive.Root>
  )
}
```

```css
.my-toc__link { display: block; padding-block: 0.125rem; }
.my-toc__link[data-active] { color: var(--bdocs-primary); }
```

The class names above are yours; the `data-*` attributes they target are the stable, documented contract.

## Styling Without a Theme Package

You can skip `@bdocs/theme-neutral` and render the primitives directly. Provide your own `surface` object to the engine and use `@bdocs/primitives` for the behavior you need — `Button`, `Menu`, `Tabs`, `Disclosure`, `Popover`, `Tooltip`, `Breadcrumbs`, `Group`, `ScrollSpyProvider` and the rest. No framework-generated class names to reverse-engineer.
